# Contributing to `@vayo/core-sdk`

Thanks for your interest in contributing! This document explains how the
project is structured, how to propose changes, and the rules you should
be aware of before opening a pull request.

## How this repository is organized

**Important:** the public GitHub repository you are reading (the `vayo-core-sdk`
mirror) is **not the canonical source of truth**. The SDK is developed
inside the private Vayo Finance monorepo at `packages/core-sdk/`, and
this public repository is a **one-way mirror** updated automatically by
a GitHub Actions workflow on every release tag.

```
   ┌──────────────────────────────┐
   │ vayo-finance (private)       │  ← source of truth
   │ packages/core-sdk/           │
   │   ├── src/                   │
   │   ├── tests/                 │
   │   ├── openapi.json           │  ← generated from live API routes
   │   └── ...                    │
   └──────────────┬───────────────┘
                  │ git subtree split
                  │ on tag `core-sdk-v*`
                  ▼
   ┌──────────────────────────────┐
   │ vayo-core-sdk (public)       │  ← this repo, one-way mirror
   │   (main branch force-pushed) │
   └──────────────────────────────┘
```

**Consequences for contributors:**

- Pull requests opened against the public mirror are **not merged directly**
  into `main`. The maintainers apply them as patches inside the private
  monorepo, re-run the full test suite, and the next release tag mirrors
  the change back out. You will see the commit on `main` with a
  `Co-Authored-By:` line crediting you.
- Force-pushes to `main` are expected — they come from the mirror workflow.
  Do not rebase on top of in-flight PRs.
- Issue trackers, discussions, releases, and security advisories all live
  on the public mirror. That's the right place for bug reports and feature
  requests.
- The `src/generated/` directory is produced by Kubb from `openapi.json`
  and is **gitignored** — you do not check it in. Run `bun run gen` to
  regenerate it locally.

If you need the workflow to be faster (e.g. a security fix), contact
**security@vayo.finance** or open a GitHub Security Advisory on this repo.

## Before you start

1. **Search existing issues and PRs** to avoid duplicating work.
2. **Open an issue first** for anything larger than a one-liner. Describe
   the use case, the proposed API, and the alternatives you considered.
   This saves everyone time compared to opening a PR that gets rejected
   for scope reasons.
3. **Security issues:** do **not** file a public issue or PR. See
   [SECURITY.md](./SECURITY.md) for the responsible disclosure process.
4. **Read the design docs.** The SDK is a thin layer over the Vayo
   Partner API — many questions you might have are already answered in:
   - [`README.md`](./README.md) — method reference + usage patterns
   - The Vayo Partner Platform deep-dive (linked from the README)
   - The Mode S orchestrator contract: [`src/mode-s/redeem.ts`](./src/mode-s/redeem.ts)

## Development setup

You need Bun 1.2.22 or later (`bun --version` to check).

```bash
# Clone the public mirror
git clone https://github.com/vayo-finance-labs/vayo-core-sdk.git
cd vayo-core-sdk

# Install dependencies
bun install

# Regenerate the kubb client from openapi.json
bun run gen

# Run the full test suite
bun test

# Typecheck
bun run typecheck

# Lint + format
bun run lint
bun run lint:fix

# Build (ESM + CJS + .d.ts)
bun run build
```

All verification steps must pass locally before you open a PR. CI will
run the same commands on your branch.

## Pull request process

### Scope rules

- **One concern per PR.** Mixing a bug fix with a refactor makes review
  harder and increases the chance of a rollback. Split them into two PRs.
- **No unrelated "drive-by" changes.** Do not reformat files you did not
  touch, do not bump unrelated dependencies, do not fix typos outside the
  lines you are editing.
- **Do not edit `src/generated/`** — it is regenerated by Kubb. If you
  need a new route or a type change, update `openapi.json` in the private
  monorepo (maintainer task) and re-run `bun run gen`.
- **Do not add runtime dependencies** without explicit maintainer approval.
  The SDK has **zero runtime deps** by design — this is a marketing
  guarantee we want to preserve. Dev dependencies are fine.
- **Keep the bundle size small.** Run `bun run build` and check that
  `dist/index.js` has not grown significantly. If your change adds more
  than ~5 KB to the main bundle, justify it in the PR description.

### What makes a good PR

- **Tests.** Every behavioral change needs a test. The SDK has four test
  files in `tests/` — add to the relevant one or create a new file. All
  tests must run without network, DB, or real Privy/Solana RPC calls
  (see `tests/mode-s-redeem.test.ts` for the stubbed-dependencies pattern).
- **Apache 2.0 header.** New source files must start with the standard
  header:
  ```ts
  // Copyright 2026 Vayo Finance Labs
  // SPDX-License-Identifier: Apache-2.0
  ```
- **`CHANGELOG.md` entry.** Add a line to the "Unreleased" section
  following the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
  format (`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`).
- **Clear commit messages.** We follow the convention from the Vayo
  monorepo: `type(scope): description` where type is one of
  `feat`, `fix`, `refactor`, `docs`, `style`, `test`, `chore`, `perf`
  and scope is typically `sdk` for this package.
- **DCO sign-off.** Every commit must be signed off via
  `git commit -s` — see the "Developer Certificate of Origin" section
  below.

### Developer Certificate of Origin (DCO)

We use the [Developer Certificate of Origin](https://developercertificate.org/)
instead of a traditional CLA. To sign off a commit, run:

```bash
git commit -s -m "fix(sdk): correct idempotency key forwarding on supply-allocated"
```

This appends a `Signed-off-by:` trailer to your commit message using the
name and email from your git config. By adding the sign-off you certify
that you have the right to submit the code under the project license
(Apache 2.0), per the DCO text.

Unsigned commits will be blocked by the [DCO GitHub App](https://github.com/apps/dco).
If you forget to sign off, amend your commit with `git commit -s --amend`
and force-push.

### Review and merge

- A maintainer will review your PR within 5 business days. Security fixes
  are prioritized.
- We may ask you to split, rebase, or refactor the PR. Don't take it
  personally — it keeps the diff reviewable.
- Once the PR is approved, it is **closed without merging** on the public
  mirror and the changes are applied to the private monorepo. You will see
  a commit referencing your PR and `Co-Authored-By: Your Name <you@...>`
  when the next release is mirrored back.
- The `CHANGELOG.md` entry lands in the release notes when the version
  tag is cut.
